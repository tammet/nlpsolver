A prover found a proof. The proof used invented implication rules that were
added to the problem as guesses. Nobody has checked them.

You are shown ONE of those rules, on its own. You are not shown the passage it
came from, the question, any other invented rule, or the proof. That is
deliberate. Your job is to say whether this rule stands up as a rule.

Judge whether the displayed premises, by themselves, normally support the
conclusion. You may use ordinary word meaning, but no additional fact from the
passage. If a relation between two objects or events is needed and is not a
premise, report it as a missing condition.

HOW TO READ A RULE

Each atom is a JSON array: the first item is the predicate, the rest are its
arguments. A word beginning `?` is a variable standing for anything.

    ["isa", CLASS, THING]

means that THING is an instance or subtype of CLASS. For example,
`["isa","bird","Tweety"]` means Tweety is a bird, and

    ["isa","bassoon","?X"] -> ["isa","woodwind","?X"]

says that every bassoon is a woodwind. That rule runs in the sensible
direction; its reverse, `["isa","woodwind","?X"] -> ["isa","bassoon","?X"]`,
says every woodwind is a bassoon and is false. Read `isa` in this order before
you decide that a rule is reversed.

For other predicates the arguments are in the order the pipeline writes them:
`["is rel2","owns","?X","?Y"]` means `?X` owns `?Y`, and
`["is rel2","in","?X","?Y"]` means `?X` is in `?Y`.

A variable name means the same thing everywhere in the rule. The FORMAL READING
is produced by a program from the rule itself. It is the meaning to judge. The
rule holds for every value of its variables: a variable that no premise
restricts ranges over everything.

The rule is defeasible. Read A -> B as "normally, if A then B". Rare exceptions
are allowed. An ORDINARY counterexample is not a rare exception: if the premises
can easily hold while the conclusion fails, the rule is too broad.

WHAT THE GLOSS LINES MEAN

    READS AS         the same atom with each internal name replaced by the
                     words the pipeline recorded for that name
    SOURCE WORDING   the original relation this atom was converted from,
                     printed with its own local variable names `?U1`, `?U2`
    NAMED IN THE PASSAGE AS   the words a constant stands for
    QUERY-CREATED PLACEHOLDER   a name the question introduced, not a thing
                                anyone stated exists
    ENCODING CONSTANT   a name the converter uses for a world or a context
    NO STORED GLOSS  nothing was recorded; judge the atom as written

These lines name things. They state no facts about them.

HOW THE PREMISES CONNECT

You are given the groups the premises fall into. Two premises are in the same
group when they mention the same variable, constant or nested term. This is a
description, not a verdict. Premises in separate groups sometimes work together
anyway, for example a general rule plus an independent condition. But if the
conclusion is about a thing that one group mentions and the reason for the
conclusion lives in another group, the relation joining them is missing from the
rule. Say so under MISSING_CONDITION.

HOW TO ANSWER

Write exactly this block, with the rule's own id in place of <rule id>:

    ASSESS_LOGIC <rule id>
    DIRECTION: CORRECT | WRONG | UNCERTAIN
    BODY_SUFFICIENT: YES | NO | UNCERTAIN
    MISSING_CONDITION: NONE | <short exact condition>
    ORDINARY_COUNTEREXAMPLE: NONE | <short counterexample>
    REASON: <one short explanation using only the displayed rule>

The fields mean:

    DIRECTION         whether the implication runs the right way and the
                      participants sit in the right places
    BODY_SUFFICIENT   whether the premises, by themselves, normally support the
                      conclusion
    MISSING_CONDITION one condition the rule needs and does not state. Write it
                      as a short phrase or as an atom, for example
                      `Heck cattle were bred back`
    ORDINARY_COUNTEREXAMPLE  an everyday case where the premises hold and the
                      conclusion fails

Write BODY_SUFFICIENT: NO whenever you have to supply a fact yourself to make
the conclusion follow. Name that fact under MISSING_CONDITION.

Write the block and nothing else.
