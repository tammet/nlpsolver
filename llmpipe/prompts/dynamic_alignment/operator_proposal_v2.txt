A logic pipeline translated a reasoning problem into logic and asked a prover
the question. The prover returned nothing. Below you are shown the problem, the
atoms the translation produced, the words the problem uses, the expressions the
prover was working on when it stopped, and a library of construction operators.

WHAT MAY HAVE GONE WRONG

More than one thing can leave a prover with nothing, and they need different
answers:

  * the English says something the translation never wrote down — a translation
    repair, not an abstraction;
  * an ordinary background fact or inference step is missing, of the kind any
    reader would supply without thinking about wording;
  * the translation wrote the same idea in two different shapes, so the two
    halves never met — this is what the operators below are for;
  * nothing is wrong: the question does not follow, and no rule should be added.

The expressions listed near the unresolved interface are candidates, not
established gaps. The search that produced them frequently could not tell an
unavailable expression from one it simply never reached. Do not assume something
must be added.

WHAT YOU NAME

You do not write the rule. You name its parts and code builds it:

  an operator   one name from the library below
  a target      what the rule should CONCLUDE: a group id (G3), a word id (L7),
                or the label of an occurrence (O7.label)
  its slots     each operator lists named slots; fill each with occurrence ids
  guards        occurrence ids that must also hold, or NONE

Code derives every compatible argument mapping from what you name, connects the
variables, quantifies, checks the result, and refuses it if it does not hold
together. You never write a quantified formula and never choose which argument
lines up with which.

Two things code will do for you, so do not spend effort on them:

  * **Direction.** For the operators marked as building both directions, name
    the two wordings and code emits `A implies B` and `B implies A` as separate
    hypotheses. Choosing the useful one is not your problem.
  * **A missing slot.** If you leave a required slot empty, code enumerates
    every occurrence that could fill it and builds each as a separate
    alternative. Naming it yourself is better — you can see the English and code
    cannot — but omitting one is not fatal.

WHAT WILL BE REFUSED

  * a slot filled by an occurrence of the wrong shape (the slot says what shape
    it needs);
  * a conclusion containing a variable no premise binds;
  * a guard that contradicts the conclusion, or repeats it;
  * promoting a word that is not a concept — a name, a number, a control value
    like `none`, or a converter token;
  * `other_restructure`, which builds nothing on purpose.

QUESTIONS ARE NOT ASSERTIONS

Lines marked `question` come from the question. They tell you which words and
which shape are at issue. They are not evidence that the expression is true and
not evidence that it is false. A word that appears only in the question is
available to name; it is not something the problem asserts.

WHAT MAKES A PROPOSAL GOOD

The English must support it. You should be able to point at a sentence and say:
this is the same thing said another way, or this word plainly stands to that one
as a kind to its category, as a compound to its head, or as a noun to its verb.
Do not propose a rule because it would make the prover succeed. A rule that
reaches the answer and is not supported by the English is worse than no rule.

Prefer the guards that keep a rule honest. If a rule should only fire for
sailors, name the atom that says `sailor`.

HOW TO ANSWER

Explain your reasoning in ordinary prose, as much or as little as you need.
Then end with at most three PROPOSE lines, and nothing after them. Each line
names the operator, the target, and that operator's slots:

PROPOSE: operator=compound_head; target=G4; head=O2; modifier=O7; link=O5; guards=NONE
PROPOSE: operator=argument_label_promotion; target=L9; carrier=O3; subject_premise=O8; guards=O4

(Those two lines are shape examples. A `compound_head` proposal of that shape
would build `isa(harbour master, x)` from an atom about mastering a harbour plus
a class atom saying the other participant is a harbour; a promotion of that
shape would turn the word `pottery`, which appears in the logic only as an
argument of `made of`, into something a thing can be.)

If no construction in this library fits what you can see, write one line instead:

REPORT: no_abstraction_needed
REPORT: ordinary_inference_gap
REPORT: translation_repair
REPORT: unsupported_construction

Use ids exactly as printed. Only those final lines are read; nothing is
recovered from your prose.
