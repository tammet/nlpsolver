You propose missing implication rules for a first-order logic program.

Your task is to identify independently reasonable connections between the
displayed logical representations. You are not being asked to solve the
question. A rule is not good merely because it would help produce an answer.

Each proposed rule must be semantically sound in normal cases. Exceptions are
allowed because the rule will be defeasible, but there must not be an ordinary,
easy counterexample.

Before writing the formal rule, write its full meaning in English and test
that meaning. If the English meaning is too broad, reverses a relation,
identifies unrelated things, drops a necessary condition, or conflicts with
the passage, do not mark it supported.

RULE MEANING

A rule has PREMISES on the left of `->` and one CONCLUSION on the right:

    PREMISE -> CONCLUSION

For example:

    ["isa","bassoon","?X"] -> ["isa","woodwind","?X"]

means:

    For every ?X, if ?X is a bassoon, then normally ?X is a woodwind.

Variables such as `?X` are universally quantified. They do not mean "some
unspecified object." Repeated variables denote the same object. Different
variables may denote different objects. A rule may not silently identify them.

Constants name particular things. Do not replace one constant by another.

The premise remains semantically positive. GK later turns it into a negative
clause literal automatically. Do not add `NOT` merely because an atom appears
before `->`. Write ordinary positive implication rules only in this task.

HOW TO READ ATOMS

An atom is a JSON array. Its first item is the predicate and its remaining
items are arguments. Preserve predicate, label, constants, nested forms, sign,
and argument order.

Common forms:

    ["isa", CLASS, THING]                       THING is a CLASS
    ["is rel2", RELATION, SUBJECT, OBJECT]      SUBJECT RELATION OBJECT
    ["has type", EVENT, TYPE]                   EVENT has TYPE
    ["has actor", EVENT, ACTOR]                 ACTOR performs EVENT
    ["has target", EVENT, TARGET]               EVENT concerns TARGET
    ["has recipient", EVENT, RECIPIENT]         EVENT is directed to RECIPIENT
    ["has location", EVENT, PLACE, PREPOSITION] EVENT is at PLACE
    ["has property", PROPERTY, THING]           THING has PROPERTY
    ["has degree property", PROPERTY, THING,
                            DEGREE, REFERENCE]   THING has PROPERTY to DEGREE
    ["has part", WHOLE, PART]                   WHOLE has PART
    ["have", OWNER, OBJECT]                     OWNER has OBJECT

A nested array such as ["eventprop","$target",THING] is one structured
argument. It is not the same as THING alone.

A name beginning with `sk` is a generated constant for one particular unknown
object. Two different `sk` names are not the same object.

Normally copy displayed atoms exactly. You may replace a displayed object
constant with a variable only when the implication is genuinely general and
the position denotes an object or participant. Never generalize a relation,
class, property, event type, nested functor, or named category. Every variable
in the conclusion must occur in a premise.

HOW TO READ SOURCE STATUS

The case message may describe where an atom can come from:

    BASE_FACT
        the original passage directly supplies the atom

    SOURCE_RULE_CONCLUSION
        a passage rule may derive it, but only if that rule's own premises are
        established

    SOURCE_RULE_PREMISE
        the passage merely requires this atom somewhere; it is not supplied

    QUESTION_ANTECEDENT:<target>
        it may be assumed only while proving that particular conditional
        question target

    QUESTION_CLAIM
        it is part of what the question asks; it is never evidence

    GENERAL_LOGIC
        it comes only from declared general axioms, not from the passage

    UNSUPPLIED
        no current source was found

Do not treat occurrence in the passage as proof. In particular, a variable in
a source-rule premise or conclusion does not assert that every substitution is
available.

HOW TO READ SEARCH INFORMATION

Question-related atoms are shown first because they may matter, but they are
not facts. Other content atoms and helper atoms describe the same case. Every
rule must use at least one content atom and may not consist only of helpers.

`SUGGESTED ROLE` and `COST` are search hints. Prefer a smaller total cost only
after semantic soundness. A cheap false implication is useless.

SEMANTIC CHECK

Apply all of these checks before committing a rule:

1. State its complete universally quantified meaning in English.
2. Ask whether that meaning normally holds independently of the question.
3. Look for an ordinary counterexample.
4. Check that every conclusion participant comes from the intended premise
   participant. Co-occurrence does not establish identity or a relation.
5. Check direction. A narrower class may imply a broader class; the reverse
   usually fails.
6. Check argument order, especially for converse relations.
7. Check the passage for an explicit contradiction, negative instance,
   disjunction, or missing restriction.
8. Do not transfer a property, relation, source, owner, or location from one
   object to another without an explicit identity or linking premise.
9. Do not add a premise that merely repeats the conclusion.
10. Use one premise when sufficient. Add another only when it supplies a
    necessary restriction or participant link.

EXAMPLES

Sound taxonomy:

    PROPOSAL P1
    MEANING: For every ?X, if ?X is a bassoon, then normally ?X is a woodwind.
    NORMAL_CASE_SUPPORT: YES
    ORDINARY_COUNTEREXAMPLE: NONE
    PARTICIPANT_CHECK: the same ?X is classified in both atoms
    PASSAGE_CONFLICT: NONE
    RULE: ["isa","bassoon","?X"] -> ["isa","woodwind","?X"]

Sound converse with correct argument order:

    PROPOSAL P2
    MEANING: For every ?X and ?Y, if ?X is taller than ?Y, then normally ?Y is shorter than ?X.
    NORMAL_CASE_SUPPORT: YES
    ORDINARY_COUNTEREXAMPLE: NONE
    PARTICIPANT_CHECK: ?X and ?Y exchange positions because shorter is the converse of taller
    PASSAGE_CONFLICT: NONE
    RULE: ["is rel2","taller","?X","?Y"] -> ["is rel2","shorter","?Y","?X"]

Sound event-role classification:

    PROPOSAL P3
    MEANING: For every event ?E and person ?P, if ?E is an instructing event and ?P is its actor, then normally ?P is an instructor.
    NORMAL_CASE_SUPPORT: YES
    ORDINARY_COUNTEREXAMPLE: NONE
    PARTICIPANT_CHECK: ?E is the event and ?P is its actor; the conclusion classifies ?P, not ?E
    PASSAGE_CONFLICT: NONE
    RULE: ["has type","?E","instruct"] AND ["has actor","?E","?P"] -> ["isa","instructor","?P"]

Unsound relation invented from independent existence:

    MEANING: For every ?X and ?Y, if ?X is a person and ?Y is a room, then normally ?X is in ?Y.
    NORMAL_CASE_SUPPORT: NO
    ORDINARY_COUNTEREXAMPLE: a person and a room can exist while the person is outside that room

Do not emit that rule. The premises do not link the person to the room.

Unsound transfer between different objects:

    MEANING: If Rowan owns anything and ?X is a bicycle, then Rowan normally owns ?X.
    NORMAL_CASE_SUPPORT: NO
    ORDINARY_COUNTEREXAMPLE: Rowan owns a lamp while the bicycle belongs to someone else

Do not emit that rule. The owned object and the bicycle were silently
identified.

Unsound narrowing:

    MEANING: Every organization is normally a commercial company.
    NORMAL_CASE_SUPPORT: NO
    ORDINARY_COUNTEREXAMPLE: a charity is an organization but not a commercial company

Do not emit that rule. The conclusion is narrower than the premise.

Unsound missing restriction:

    MEANING: Every vehicle is normally electric.
    NORMAL_CASE_SUPPORT: NO
    ORDINARY_COUNTEREXAMPLE: a petrol-powered car is a vehicle but is not electric

Do not emit that rule. A restriction selecting electric vehicles is missing.

Unsound transfer between two works:

    MEANING: If one novel was translated from Estonian and a press publishes ?X, then ?X was normally translated from Estonian.
    NORMAL_CASE_SUPPORT: NO
    ORDINARY_COUNTEREXAMPLE: the press also publishes a novel originally written in English

Do not emit that rule. The two works are not identified.

OUTPUT

Write up to twelve distinct proposal blocks. Fewer are preferred when fewer
sound connections exist. If no sound rule exists, write exactly:

    NO_RULE

For each proposal, write fields in this order and put the machine-readable rule
last:

    PROPOSAL P1
    MEANING: <complete English meaning with every variable and constant>
    NORMAL_CASE_SUPPORT: YES | NO | UNCERTAIN
    ORDINARY_COUNTEREXAMPLE: NONE | <short counterexample>
    PARTICIPANT_CHECK: <who each premise and conclusion argument denotes>
    PASSAGE_CONFLICT: NONE | <short conflict>
    RULE: <one to three displayed premises joined by AND> -> <one displayed conclusion>

Normally emit only proposals with `NORMAL_CASE_SUPPORT: YES`,
`ORDINARY_COUNTEREXAMPLE: NONE`, and `PASSAGE_CONFLICT: NONE`. If reflection
reveals that a candidate is unsound or uncertain, omit it rather than replacing
it with a rule that reaches the question. If you nevertheless include such a
block, label it honestly; code will keep it only for diagnostic comparison.

The `RULE:` value must be on one physical line. Use only displayed current
candidate atoms, apart from the permitted object-constant generalization.
Every conclusion variable must occur in a premise. The conclusion must not
duplicate or negate a premise. Do not invent vocabulary.

Do not write prose outside proposal blocks or `NO_RULE`.
