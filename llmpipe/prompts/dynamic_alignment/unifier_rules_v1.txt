A logic pipeline translated one reasoning problem into predicate logic and the
prover found no answer. Below are the signed atom patterns that translation
produced, in the prover's own notation.

Your job is to say which of these patterns likely imply which others.

HOW TO READ AN ATOM

Each atom is a JSON array. The first item is the predicate, exactly as the
pipeline writes it; the rest are its arguments, exactly as the pipeline writes
them. A word beginning `?` is a variable standing for anything; every other
word is a fixed constant — a class, a relation name or a particular thing.
`NOT` in front of an atom means its negation.

    ["isa","cupcake","?X"]              ?X is a cupcake
    NOT ["isa","cupcake","?X"]          ?X is not a cupcake
    ["is rel2","part of","?X","?Y"]     ?X is part of ?Y

`existing resolution partners: N` counts how many literals already in the
theory could combine with that pattern in a proof step. A pattern with FEW
partners is one the prover currently has little to do with — often exactly the
place where a missing connection sits. `count unavailable` means the pattern's
predicate does not occur in the converted theory at all.

A pattern marked QUESTION COMPONENT is part of what the question asks. It is
not something the passage asserts. The same pattern's opposite sign is shown as
a separate line because a proof may need either.

WHAT TO WRITE

Zero or more implication rules, each on its own line, in exactly this form:

    RULE: ["isa","bassoon","?X"] -> ["isa","woodwind","?X"]
    RULE: ["is rel2","plays in","?X","?Y"] AND ["isa","orchestra","?Y"] -> ["isa","musician","?X"]
    RULE: ["is rel2","conducts","?X","?Y"] -> ["is rel2","leads","?X","?Y"]
    RULE: ["isa","soloist","?X"] -> NOT ["isa","conductor","?X"]

Those four are format examples only; their words have nothing to do with this
problem.

RULES OF THE NOTATION

  * one `->`, one conclusion, at most three premises joined by `AND`;
  * every atom is a JSON array, written exactly as the patterns above are
    written — same predicate, same number of arguments, same argument order;
  * variables begin with `?`; the same variable used twice means the same
    thing twice; a variable in the conclusion must also appear in a premise;
  * use only predicates, relation names, class words and constants that appear
    in the list you were shown;
  * keep a named thing where the list shows a named thing — do not replace it
    with a variable;
  * `NOT` goes outside an atom, never inside it.

WHAT MAKES A USEFUL RULE

  * it connects two patterns that say the same or a closely related thing in
    different words or different structures;
  * it is a plain background truth an ordinary reader would accept;
  * it lets one pattern in the list reach another, especially a question
    component.

Both directions may be worth writing when both are plausible: write them as two
rules. Do not write a rule that merely restates a premise as itself.

You are not being asked to prove anything, and nothing here tells you what the
answer should be. Do not try to work out the answer and then write rules that
would produce it.

HOW TO ANSWER

Write as much or as little prose as you like — it is kept but not read by the
program. Then write your rules, at most twelve, each on its own line beginning
`RULE:`. Only lines beginning `RULE:` are read, and a line that does not parse
is discarded rather than repaired.

If nothing in the list plausibly implies anything else, write no RULE lines.
